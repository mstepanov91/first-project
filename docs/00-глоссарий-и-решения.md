# Глоссарий и журнал решений (ADR)

> Координационный документ проекта. **Единый источник правды** по терминологии и принятым
> решениям. Все участники (включая субагентов) читают его первым и предлагают изменения;
> интегрирует правки только лид-оркестратор.

## Часть 2. Журнал решений (ADR)

Формат: **ADR-N — Заголовок** · *Статус* · Контекст → Решение → Последствия.

### ADR-1 — Целевой рынок и позиционирование · Принято
**Контекст:** Figma становится недоступной в ряде стран (санкции/блокировки).
**Решение:** Строим аналог для таких рынков; ключевая ценность — доступность +
резидентность данных + локальные платежи.
**Последствия:** Все продуктовые/архитектурные решения проверяются на независимость от
внешних (подсанкционных) провайдеров.

### ADR-2 — Охват MVP · Принято
**Контекст:** Линейка Figma огромна (Design, FigJam, Slides, Make, Sites, Dev Mode…).
**Решение:** MVP = **ядро**: векторный редактор UI + real-time коллаборация + dev-хэндофф.
FigJam, Slides, Sites, AI/Make — за рамками MVP (в роадмапе как «Будущее»).
**Последствия:** Спецификации и сайзинг считаем для ядра; экосистемные фичи не раздувают MVP.

### ADR-3 — Модель развёртывания · Принято
**Контекст:** Нужна независимость от внешней инфраструктуры.
**Решение:** Основной сценарий — **локальный SaaS в стране** на арендованных облачных
серверах локальных провайдеров. Self-hosted/on-prem — как будущая опция.
**Последствия:** Отказ от внешних CDN/облаков; объектное хранилище — S3-совместимое локальное
(или MinIO); платежи — локальные провайдеры.

### ADR-4 — Минимизация инфраструктуры на старте · Принято
**Контекст:** Ограниченный бюджет на старте, неопределённая аудитория.
**Решение:** Стартуем с **моно-сервера** (Вариант A): всё в docker-compose на одном VM.
Масштабируемся по тирам T0→T1→T2.
**Последствия:** Архитектура сервисов модульная, но упакована для запуска на одной машине;
горизонтальное масштабирование закладывается, но не активируется на T0.

### ADR-5 — Подход к рендерингу · Принято
**Контекст:** Figma использует C++→WASM + кастомный GPU-рендерер (WebGL→WebGPU) ради
производительности; это дорого в разработке. Нужен баланс скорости выхода MVP и
производительности.
**Решение:** Рендерер MVP — **TypeScript + WebGL** (лёгкий движок класса PixiJS) за
абстракцией `Renderer`, отвязанной от модели документа. Canvas2D отвергнут (CPU-bound, не
тянет большие файлы); нативный C++/Rust→WASM + WebGL/WebGPU — отложен на фазу
масштабирования (дорог, тяжёлый бандл без CDN, дорогой FFI-мост). Эволюция: WebGL-оптимизации
(тайлинг, dirty regions, OffscreenCanvas) → вынос горячего ядра в Rust→WASM.
**Последствия:** Быстрый MVP и простой найм ценой производительности на очень больших
файлах; абстракция `Renderer` сохраняет путь к нативному ядру. Детали — `docs/04`.

### ADR-6 — Протокол синхронизации · Принято
**Контекст:** Нужен real-time мультиплеер; чистый CRDT/OT избыточны.
**Решение:** **Server-authoritative property-level Last-Writer-Wins** по логическим часам
поверх WebSocket; fractional indexing для порядка/реპарентинга; in-memory состояние на
sync-узле, отдельная персистентность.
**Последствия:** Простая модель конфликтов; узким местом мультиплеер-узла станет CPU при
активных правках (см. сайзинг в `docs/06`).

### ADR-7 — Совместимость формата `.fig` · Предложено
**Контекст:** Миграция пользователей с Figma требует импорта `.fig` (как у Pixso/MasterGo).
**Решение (черновик):** Импорт `.fig` — важный фактор миграции, но технически рискованный
(проприетарный бинарный формат). Включить в роадмап как отдельный трек, не блокирующий MVP.
**Последствия:** MVP может стартовать без импорта; импорт — приоритет фазы роста.

### ADR-8 — Язык документации · Принято
**Решение:** Документация на русском; англоязычный термин — в скобках при первом упоминании.

### ADR-9 — Модель ролей и доступа · Принято
**Контекст:** Нужна модель прав, согласованная с capped-тарифами (преимущество против
per-seat Figma).
**Решение:** Роли — владелец/админ, редактор, комментатор, зритель; назначаются на уровнях
Org/Team/Project/File (RBAC). Роли «зритель»/«комментатор» НЕ тарифицируются как полные места.
**Последствия:** Биллинг считает только полные (редакторские) места; права наследуются по
иерархии. Детали — `docs/03`, `docs/04`.

### ADR-10 — Объём dev-хэндоффа в MVP · Принято
**Контекст:** Хэндофф — часть ядра MVP (ADR-2), но генерация кода объёмна.
**Решение:** В MVP — inspect, измерения, экспорт ассетов, копирование значений токенов и
базовый CSS-сниппет. Генерация кода под фреймворки и экспорт токенов в стандартных форматах
(напр. W3C Design Tokens) — «Позже».
**Последствия:** Чёткая граница MVP для `docs/03`/`docs/05`.

### ADR-11 — Версионирование и история файла · Принято
**Контекст:** Нужна история изменений; ветвление (branching) — дорогая фича.
**Решение:** В MVP — непрерывное сохранение (лог операций + снапшоты) и именованные версии.
Ветвление файлов (branching) — пост-MVP.
**Последствия:** Персистентность строится на логе операций + периодических снапшотах (см.
`docs/04`).

### ADR-12 — Открытый формат файла · Принято
**Контекст:** Урок Penpot — открытый формат (SVG+JSON) даёт владение данными и портируемость;
бинарь Figma запирает пользователя.
**Решение:** Экспорт/архив документа — в **открытый ZIP** (`document.json` + ассеты SVG/PNG).
Внутреннее runtime-представление — компактное (плоская карта узлов + лог операций + бинарные
снапшоты), не обязано совпадать с форматом обмена.
**Последствия:** Портируемость как пункт позиционирования; импорт `.fig` (ADR-7) маппится в
`document.json`.

### ADR-13 — Локализация интерфейса · Принято
**Контекст:** Figma — только английский UI; Pixso/MasterGo выигрывают локализацией на
ограниченных рынках.
**Решение:** Полная локализация UI на язык целевой страны с первого релиза; архитектура
i18n закладывается в MVP.
**Последствия:** Явный пункт дифференциации в `docs/01`; требование к фронтенду в `docs/03`.

> Новые решения добавлять последовательным номером ADR-N. Не переписывать историю —
> устаревшие решения помечать статусом «Заменено ADR-M».
