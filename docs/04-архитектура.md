# 04. Техническая архитектура

> Технический документ системного архитектора. Описывает архитектуру совместного редактора
> интерфейсов (collaborative UI design tool) — аналога Figma для рынков, где она недоступна.
> Модель развёртывания — локальный SaaS в стране (in-country SaaS, ADR-3), старт с моно-сервера
> (ADR-4). Документ детализирован для исполнения: с явными трейд-оффами (trade-offs) и
> ссылками на аналитику Figma в `src/`. Терминология — из `docs/00`; англоязычные термины —
> в скобках при первом упоминании (ADR-8).

---

## Архитектурное резюме (TL;DR)

Мы строим **клиент-серверный canvas-редактор** с real-time коллаборацией. Несущие решения:

1. **Рендерер (renderer) MVP — TypeScript + WebGL** (через лёгкий движок типа PixiJS), а не
   Canvas2D и не C++/Rust→WASM. Это компромисс: скорость вывода MVP и приемлемая
   производительность на средних файлах, с запланированной эволюцией к WASM-ядру на фазе
   масштабирования. **Финализирует ADR-5** (см. §3).
2. **Модель документа (document model)** — граф сцены (scene graph) из узлов (Node) со
   свойствами; порядок детей — через дробное индексирование (fractional indexing);
   сериализация в **открытый формат JSON + SVG-ассеты** (урок Penpot), а не проприетарный
   бинарь (§4).
3. **Синхронизация (sync)** — server-authoritative property-level Last-Writer-Wins (LWW) по
   логическим часам (logical clock) поверх WebSocket, in-memory состояние на sync-узле + лог
   операций и снапшоты в персистентности (ADR-6, §5). Не CRDT/OT — обоснование в §5.7.
4. **Бэкенд** — набор модульных сервисов (auth, files/projects/teams, multiplayer, comments,
   export-воркеры, storage-gateway), упакованных в **docker-compose на одном VM** на старте
   (ADR-4), с заделом на горизонтальное масштабирование (§6, §8).
5. **Данные** — PostgreSQL (метаданные, комментарии, лог операций), S3-совместимое объектное
   хранилище (MinIO для self-host / локальный S3), Redis (кэш, presence, pub/sub) (§7).
6. **Без внешних CDN** — статика и WASM раздаются локально (ADR-3, §8); резидентность данных и
   изоляция арендаторов (tenant isolation) — сквозное требование (§9).

Связь с аналитикой: рендеринг — `src/03-техническая-архитектура.md`; модель документа —
`src/04-модель-данных.md`; платформа/API — `src/05-платформа-разработчика.md`; импорт `.fig` —
`src/07-анализ-конкурентов.md`.

## 1. Контекст и принципы

### 1.1. Контекст
Сервис разворачивается как **локальный SaaS в стране** (in-country SaaS) на арендованных
серверах локальных провайдеров (ADR-3). Ключевая ценность продукта (см. `docs/01`) —
доступность, резидентность данных (data residency) и независимость от внешней
(подсанкционной) инфраструктуры. Это формирует жёсткие архитектурные ограничения, которых нет
у Figma.

### 1.2. Архитектурные принципы
1. **Независимость от внешних провайдеров.** Никаких внешних CDN, managed-облаков, внешних
   шрифтовых/аналитических/платёжных SDK на критическом пути. Любая зависимость проверяется
   на санкционный риск (ADR-1). Self-hosted-стек по умолчанию: PostgreSQL, Redis, MinIO/локальный
   S3 — всё открытое и разворачиваемое внутри страны.
2. **Минимум инфраструктуры на старте (ADR-4).** Один VM, docker-compose, минимум движущихся
   частей. Сложность (k8s, пул нод, отдельные кластеры БД) вводится только по мере роста тиров
   аудитории (audience tier) T0→T1→T2.
3. **Резидентность данных.** Все данные — метаданные, файлы, история, превью — физически в
   юрисдикции целевой страны. Никакой телеметрии «наружу».
4. **Модульность без преждевременного дробления.** Сервисы логически разделены по границам
   (auth, files, multiplayer…), но на T0 запускаются как контейнеры на одной машине; границы
   спроектированы так, чтобы вынести любой сервис в отдельный процесс/под без переписывания.
5. **Открытые форматы и стандарты.** Документ сериализуется в открытый формат (урок Penpot:
   SVG+JSON против бинаря Figma) — это снижает vendor lock-in и упрощает экспорт/импорт.
6. **Производительность клиента — на GPU.** Рендеринг на холсте (Canvas) — главный фактор
   ощущаемого качества; ему посвящён отдельный трек (§3).

### 2.2. Роли компонентов (кратко)
- **Клиент** — рендерер (отрисовка scene graph на GPU) + UI-слой (React) + локальная in-memory
  модель документа с undo/redo. Два канала с сервером: WebSocket (sync/presence) и HTTPS (REST,
  загрузка/раздача ассетов и WASM).
- **Шлюз/балансировщик** — TLS, раздача статики и WASM **локально** (без CDN), маршрутизация,
  sticky-сессии (sticky sessions) для прилипания WebSocket к sync-узлу.
- **Сервисы** — модульные бэкенд-компоненты (§6).
- **Хранилища** — PostgreSQL, Redis, объектное хранилище (§7).

Соответствует общей картине из `src/03-техническая-архитектура.md` (рендеринг, мультиплеер,
масштабирование), адаптированной под ограничение «один сервер, без внешних облаков».

## 3. Фронтенд-рендерер — ключевое решение (финализация ADR-5)

Рендерер — сердце редактора и главный драйвер ощущаемого качества. Figma решила эту задачу
кастомным C++→WASM-движком, выводящим на `<canvas>` через WebGL, а с 2024–2025 — через WebGPU;
рендеринг тайловый (tile-based), полностью на GPU, с антиалиасингом, масками, блюром,
blend-режимами (см. `src/03-техническая-архитектура.md`; Figma Blog: «Building a professional
design tool on the web», «Figma is powered by WebAssembly», «Figma Rendering: Powered by
WebGPU»). Это эталон, но **очень дорого в разработке**: Figma пришлось написать ещё и
собственные text layout, color picker и прочие примитивы, которые обычно даёт браузер.

### 3.1. Варианты и трейд-оффы

| Критерий | (а) TS + Canvas2D | (б) TS + WebGL (PixiJS-подобный) | (в) C++/Rust→WASM + WebGL/WebGPU |
|---|---|---|---|
| Скорость вывода MVP | **Высокая** (дни/недели) | Средняя (недели/месяцы) | **Низкая** (месяцы/годы) |
| Сложность разработки | Низкая | Средняя | **Очень высокая** |
| Производительность (большие файлы, тысячи узлов) | Низкая (CPU-bound, перерисовка) | **Хорошая** (GPU, батчинг спрайтов/геометрии) | **Эталонная** (тайлы, ручное управление памятью) |
| Качество вектора (антиалиасинг, кривые) | Хорошее «из коробки» (браузер) | Среднее (нужны шейдеры/триангуляция кривых) | Эталонное |
| Текст | Простой (браузерный) | Средний (нужен свой layout/атлас глифов) | Свой движок (сложно) |
| Размер бандла / cold start | Малый | Средний | Большой (WASM + загрузка; критично без CDN) |
| Доступ к данным со стороны UI (React) | Прямой | Прямой | Нужен FFI-мост JS↔WASM (накладные расходы) |
| Риск без CDN (раздаём локально) | Низкий | Низкий | **Повышенный** (тяжёлый WASM грузим с моно-сервера) |
| Команда / найм | Любой фронтендер | Фронтендер с graphics-опытом | Редкие C++/Rust+graphics инженеры |

**Замечания по нюансам:**
- **Canvas2D (а)** упирается в CPU: при панораме/зуме и тысячах узлов перерисовка не успевает за
  60 FPS; нет дешёвого способа батчить. Годится для прототипа, но не для целевого опыта.
- **WebGL (б)** даёт GPU-ускорение и батчинг при умеренной сложности; кривые Безье требуют
  триангуляции или SDF-подхода, текст — атласа глифов, но всё это решаемо готовыми библиотеками
  и обозримым объёмом своего кода. Хороший баланс «время выхода / производительность».
- **WASM (в)** — потолок производительности и эталон Figma, но это многомесячный трек, тяжёлый
  бандл (особенно болезненно без CDN — см. ADR-3/§8) и дорогой FFI-мост к React-UI. Несовместимо
  с принципом «минимум инфраструктуры и быстрый MVP» на старте.

### 3.2. Рекомендация для MVP
**Вариант (б): TypeScript + WebGL** через лёгкий движок (PixiJS-подобный или его форк).
Обоснование:
- Закрывает целевые сценарии MVP (векторный UI-редактор, мультиплеер, хэндофф — ADR-2) на
  средних файлах с приемлемым FPS.
- Срок вывода и стоимость разработки кратно ниже WASM-трека; команда нанимается проще.
- Архитектурно совместим с эволюцией: scene graph и модель документа (§4) не зависят от
  движка рендеринга — рендерер абстрагирован за интерфейсом `Renderer{ draw(sceneGraph,
  viewport) }`, что позволяет позже заменить реализацию.
- Без внешнего CDN бандл WebGL-движка остаётся управляемым (в отличие от тяжёлого WASM).

> **Архитектурное правило:** scene graph, модель документа и протокол синхронизации **не знают**
> о реализации рендерера. Рендерер — заменяемый адаптер. Это снижает стоимость перехода (б)→(в).

### 3.3. Путь эволюции
1. **T0 (MVP):** TS+WebGL, фокус на корректности модели и мультиплеера, не на пиксельном пределе.
2. **T1:** оптимизации в рамках WebGL — тайлинг viewport, дёрти-регионы (dirty regions),
   инстансинг, кэш растров для статичных поддеревьев, off-thread геометрия (Web Worker +
   OffscreenCanvas).
3. **T2 / фаза масштабирования:** при упоре в потолок — вынос горячего ядра рендеринга
   (геометрия, текст, тайлы) в **Rust→WASM** с выводом через WebGL/WebGPU (путь Figma), сохраняя
   ту же абстракцию `Renderer`. WebGPU — как опциональный бэкенд при достаточной поддержке
   браузеров.

### 3.4. Предлагаемый финал ADR-5 (для внесения лид-оркестратором в `docs/00`)
> **ADR-5 — Подход к рендерингу · Принято (заменяет черновик).**
> **Решение:** Рендерер MVP — **TypeScript + WebGL** (лёгкий движок PixiJS-класса), за
> абстракцией `Renderer`, отвязанной от модели документа. Canvas2D отвергнут (CPU-bound,
> не тянет большие файлы); C++/Rust→WASM отложен как цель фазы масштабирования (дорог, тяжёлый
> бандл без CDN, дорогой FFI-мост). **Путь эволюции:** WebGL-оптимизации (тайлинг, dirty
> regions, OffscreenCanvas) → при упоре в потолок вынос горячего ядра в Rust→WASM с
> WebGL/WebGPU-выводом.
> **Последствия:** Быстрый MVP и простой найм ценой компромисса по производительности на очень
> больших файлах; задел на WASM-эволюцию сохранён архитектурно.

## 4. Модель документа

См. `src/04-модель-данных.md` (иерархия Organization→…→Nodes, граф сцены, узлы/свойства, дробное
индексирование, версии).

### 4.1. Узлы и граф сцены
Документ — **граф сцены (scene graph)**: дерево узлов (Node). Узел — это `id` + `type` + набор
**свойств (properties)** + ссылка на родителя + порядковый ключ. Типы узлов MVP: `DOCUMENT`,
`PAGE`, `FRAME` (контейнер/артборд, может иметь авто-лэйаут), `GROUP`, `RECTANGLE`, `ELLIPSE`,
`VECTOR`, `TEXT`, `COMPONENT`, `INSTANCE`. Свойства — плоская карта (geometry: x/y/w/h/rotation;
fills; strokes; effects; text; layout; constraints; и т.д.).

**Ключевой приём:** документ хранится не как глубоко вложенный JSON, а как **плоская карта
узлов** `{ nodeId → { props, parentId, orderKey } }`. Дерево восстанавливается по `parentId` +
сортировке по `orderKey`. Это критично для синхронизации: операция меняет свойство **одного
узла**, а не переписывает поддерево (ровно как описано для Figma в `src/03`/`src/04`).

### 4.2. Fractional indexing (дробное индексирование)
Порядок детей внутри родителя задаётся дробным индексом — строкой-дробью из интервала (0,1)
(см. глоссарий). Вставка между двумя детьми = усреднение соседних ключей **строковой
арифметикой** (для сохранения точности), с отбрасыванием ведущего `0.` и использованием широкого
ASCII-диапазона (Figma — база 95). Реparenting (reparenting) = смена `parentId` + новый `orderKey`
в целевом родителе.

**Трейд-офф и защита:** при одновременной вставке двумя пользователями в одно место возможно
**чередование (interleaving)** — для дизайн-документа это терпимо (в отличие от текстового
редактора), что подтверждает практика Figma (Figma Blog: «Realtime Editing of Ordered
Sequences»). Чтобы избежать **коллизий ключей**, добавляем **джиттер (jitter)** — небольшую
случайную составляющую к генерируемому ключу; при совпадении ключей детерминированный
тай-брейк по `nodeId`. Это дешевле, чем гарантированная защита от чередования (которая раздувает
длину ключей).

### 4.3. Версии и история (history)
- **Undo/redo** — локальный, клиентский, на стеке инверсных операций (см. §5.6).
- **Именованные версии / автосохранения** — снапшоты документа (snapshot) в объектном хранилище
  + запись в БД (`document_versions`). Восстановление = загрузка снапшота как нового состояния.
- **Журнал изменений** — лог операций (operation log) в PostgreSQL (§5.5, §7) даёт основу для
  истории и аудита.

### 4.4. Сериализация и формат файла (урок Penpot vs Figma)
Figma использует **проприетарный бинарный формат `.fig`** — компактный, но закрытый и
непереносимый. Penpot хранит документ как **ZIP с SVG + JSON** — человекочитаемо,
версионируемо в Git, без vendor lock-in (WebSearch: Penpot vs Figma format).

**Решение:** наш формат экспорта/архива (`.файл-проекта`) — **открытый: ZIP-контейнер с
`document.json` (граф сцены: узлы, свойства, порядковые ключи, ссылки на ассеты) + папка ассетов
(SVG/PNG-вектор, изображения, шрифты-ссылки)**. Это:
- даёт переносимость и снижает lock-in (продуктовая ценность — §1.5);
- упрощает экспорт в SVG/CSS для хэндоффа;
- упрощает версионирование и диффы.

**Трейд-офф:** JSON+SVG крупнее и медленнее бинаря Figma при загрузке огромных файлов.
Митигация: внутреннее **runtime-представление компактное** (плоская карта + лог операций +
бинарные снапшоты в storage); открытый ZIP-формат — для **экспорта/импорта/архива**, не для
горячего пути синхронизации. Так мы получаем и открытость, и скорость.

> **Предложение нового термина в `docs/00`:** «Снапшот (Snapshot) — целостный слепок состояния
> документа в объектном хранилище для быстрой загрузки и восстановления версий», «Лог операций
> (Operation log) — упорядоченная последовательность применённых операций для восстановления и
> аудита».

## 5. Протокол синхронизации (ADR-6)

Реализует принятое ADR-6: **server-authoritative property-level LWW** по логическим часам поверх
WebSocket. Источник модели — `src/03-техническая-архитектура.md` (мультиплеер Figma).

### 5.1. Принцип
Сервер (sync-узел) — **единственный арбитр (server-authoritative)** финального состояния. Клиент
применяет правки **оптимистично (optimistic)** локально и шлёт операции серверу; сервер
упорядочивает их по логическим часам, разрешает конфликты по **Last-Writer-Wins на уровне
свойства (property-level)** и рассылает подтверждённые изменения всем подписчикам.

### 5.2. Формат операции (op)
Минимальная единица — **изменение одного свойства одного узла** (см. глоссарий «Операция»):

```
Op {
  fileId:   string
  nodeId:   string
  property: string        // напр. "fills", "x", "orderKey", "parentId", "_deleted"
  value:    any           // новое значение свойства (LWW-перезапись целиком)
  clock:    uint64        // логические часы (монотонные на сервере)
  sessionId:string        // тай-брейк при равных часах
  origin:   string        // клиентский локальный id операции (для ack/идемпотентности)
}
```
Создание узла = набор op, выставляющих свойства нового `nodeId`. Удаление = op `_deleted=true`
(tombstone), физическая чистка — позже, при компакции. Перемещение/реparenting = op на
`parentId` и/или `orderKey`.

**LWW-разрешение:** для каждого `(nodeId, property)` сервер хранит часы последней записи;
входящая op применяется, только если её `clock` больше (при равенстве — больший `sessionId`).
Конфликты разрешаются **на уровне свойства**, поэтому одновременное редактирование разных свойств
одного узла (один двигает, другой красит) не конфликтует.

### 5.3. Логические часы (logical clock)
Монотонный счётчик **на сервере** (sync-узел) на файл; присваивается при приёме op. Клиент
держит локальный «hint», но авторитет — серверный. Это упрощает модель против векторных часов
CRDT.

### 5.4. WebSocket-протокол и presence
- **Соединение:** клиент открывает WS к `multiplayer`-сервису, проходит auth (токен сессии),
  подписывается на `fileId`. Балансировщик закрепляет соединение за нодой (sticky session).
- **Начальная синхронизация:** сервер шлёт текущий снапшот состояния файла (из in-memory или из
  storage) + текущие часы; далее — поток подтверждённых op.
- **Поток сообщений:** `op` (правка), `ack` (подтверждение по `origin`), `presence` (курсор,
  выделение, viewport), `join/leave`.
- **Присутствие (presence):** эфемерно, **не персистится** — живёт в Redis (TTL) и
  рассылается через pub/sub между нодами. Курсоры/выделения других пользователей рисует рендерер.

### 5.5. In-memory состояние и персистентность
- **In-memory на sync-узле:** для каждого «горячего» файла нода держит актуальное состояние
  (плоская карта узлов + часы по свойствам) в памяти — это даёт мгновенное применение и рассылку.
  Узкое место (по ADR-6) — **CPU sync-узла при активных правках**; драйвер сайзинга — число
  одновременных активных редакторов на файл (§8).
- **Персистентность (асинхронно, вне горячего пути):**
  1. **Лог операций (operation log)** — append в PostgreSQL (партиции по `fileId`), батчами.
  2. **Снапшоты (snapshots)** — периодически и по триггерам (N операций / T минут / при выгрузке
     файла из памяти) пишем целостный слепок в объектное хранилище; в БД — указатель и часы.
  3. **Восстановление файла:** загрузить последний снапшот + докатить лог операций после него.
- **Компакция (compaction):** после снапшота старый лог можно усечь; tombstone-узлы вычищаются.

### 5.6. Undo/redo
**Локальный, клиентский.** Каждая пользовательская правка порождает прямую op + **инверсную op**
(старое значение свойства); они кладутся в локальный стек. Undo = применить инверсную op
локально и отправить её на сервер как обычную правку (она пройдёт LWW и разойдётся всем). Это
**не глобальный undo** — пользователь откатывает свои действия; так же устроено у Figma
(см. `src/03`). Трейд-офф: при конкуренции undo может «не вернуть» ровно прежнее состояние, если
кто-то уже переписал то же свойство — приемлемо для дизайн-документа.

### 5.7. Почему не чистый CRDT/OT
- **OT (operational transformation)** требует сложных функций трансформации для каждого типа
  операции и пары; сложен и хрупок вне текста.
- **CRDT** даёт сходимость без центрального арбитра, но ценой: метаданные (версии/tombstone) на
  каждый узел/символ, рост памяти, сложность gc, и всё равно нетривиальная семантика для
  графики. Нам **не нужна** офлайн-конвергенция произвольной длины: у нас уже есть центральный
  сервер (ADR-3 — локальный SaaS), поэтому server-authoritative LWW + fractional indexing
  **проще и достаточно** (ADR-6; подтверждено практикой Figma — Figma Blog «How Figma's
  multiplayer technology works»). Чередование при fractional indexing терпимо для дизайна (§4.2).

### 5.8. Offline-режим
MVP — **деградирующий онлайн**, не полноценный офлайн-CRDT:
- При обрыве WS клиент продолжает применять правки **локально** (оптимистично), копит исходящие
  op в очереди.
- При восстановлении соединения — **reconnect + replay**: клиент сверяет серверные часы,
  отправляет накопленные op (они проходят LWW). При длительном офлайне и расхождении — повторная
  загрузка снапшота с предупреждением о возможной потере конкурентных правок.
- Полноценный надёжный офлайн (длительная работа без сети с гарантией слияния) — **за рамками
  MVP**, трек фазы роста (там, где LWW недостаточно, точечно рассмотреть CRDT для отдельных
  поддеревьев). Соответствует офлайн-разделу `src/03`.

> **Предложение в `docs/00`:** термины «Снапшот», «Лог операций», «Sticky-сессия (Sticky
> session) — закрепление WebSocket-клиента за конкретной нодой мультиплеера через
> балансировщик».

## 6. Бэкенд-сервисы

Модульные сервисы с явными границами. На T0 — контейнеры в одном docker-compose; границы
позволяют вынести каждый в отдельный процесс/под. Взаимодействие — синхронно по HTTP/gRPC для
команд и через Redis pub/sub для событий/presence.

| Сервис | Ответственность | Зависимости |
|---|---|---|
| **auth** | Аутентификация (OAuth2 / собственные сессии), выдача/валидация токенов сессий, RBAC-политики (роли: owner/admin/editor/viewer на уровне team/project/file), SSO (Org/Enterprise — позже). | PostgreSQL (пользователи, сессии, роли), Redis (сессии/блэклист токенов). |
| **files / projects / teams** | CRUD файлов, проектов, команд; права доступа (RBAC-проверки), членство, шаринг по ссылке; метаданные файла; создание версий. | PostgreSQL, storage-gateway (снапшоты/ассеты). |
| **multiplayer** | WebSocket-эндпоинт, sync-узел: in-memory состояние горячих файлов, приём/упорядочивание op (LWW), рассылка, presence. **Stateful**, прилипает по sticky-сессии. | Redis (presence, pub/sub между нодами), PostgreSQL (лог операций), storage (снапшоты), auth (валидация). |
| **comments** | Треды комментариев, привязка к координатам/узлам, упоминания, нотификации. | PostgreSQL, multiplayer (live-уведомления через pub/sub). |
| **export / render-воркеры** | Фоновая генерация **превью/тумбнейлов (thumbnails)**, экспорт ассетов (PNG/SVG/PDF), серверный рендер. Очередь задач; рендер тем же ядром, что клиент (Node+headless GL / общий код). | Redis (очередь), storage (вход/выход), PostgreSQL (статусы). |
| **storage-gateway** | Единая абстракция над S3-совместимым хранилищем: загрузка/выдача ассетов, снапшотов, превью; presigned-URL; квоты/проверка прав (через files). Изолирует остальные сервисы от конкретной реализации (MinIO/локальный S3). | Объектное хранилище, files (права). |

**Границы и взаимодействие (ключевое):**
- **Запись в документ идёт только через multiplayer** (даже одиночное редактирование = WS-сессия
  на 1 пользователя) — единый путь упрощает консистентность.
- **files/projects/teams** — это плоскость управления (control plane): права, метаданные,
  версии; не трогает горячий путь правок.
- **export-воркеры** — асинхронные, не на критическом пути UI; масштабируются числом воркеров.
- **storage-gateway** — единственный, кто знает про S3-реализацию; смена MinIO↔локальный S3 не
  затрагивает другие сервисы (принцип независимости, §1.1).

Связь с `src/05-платформа-разработчика.md`: будущие REST API / Webhooks / Plugin API ложатся
поверх этих же сервисов (files/projects/teams + auth) — на MVP не входят (ADR-2), но границы
заложены.

## 7. Данные и хранилище

### 7.1. PostgreSQL — метаданные, комментарии, лог операций
Реляционная БД для всего, что требует целостности и запросов. Ключевые сущности (кратко):

```
teams(id, name, created_at, plan)
team_members(team_id, user_id, role)                       -- RBAC
users(id, email, name, auth_provider, password_hash?, created_at)
projects(id, team_id, name, created_at)
files(id, project_id, name, current_version_id, current_snapshot_ref,
      server_clock, created_at, updated_at)
file_acl(file_id, subject_id, subject_type, role)          -- RBAC на файл/шаринг
document_versions(id, file_id, snapshot_ref, label, created_by, created_at)
operations(id, file_id, node_id, property, value JSONB,    -- лог операций
           clock BIGINT, session_id, created_at)           -- партиции по file_id
comments(id, file_id, node_id?, x, y, author_id, body, thread_id, resolved, created_at)
sessions(id, user_id, expires_at, ...)                     -- может жить в Redis
```
Заметки: `operations` партиционируется по `file_id` и периодически усекается после снапшота
(§5.5). `value` — JSONB (свойство перезаписывается целиком — LWW). Все таблицы несут `team_id`
по цепочке для **изоляции арендаторов** (§9).

### 7.2. Объектное хранилище — S3-совместимое (MinIO / локальный S3)
Хранит крупные бинарные артефакты, не лезущие в БД: **снапшоты документов**, **ассеты**
(изображения, шрифты, SVG), **превью/тумбнейлы**, **экспортные файлы**, **архивные ZIP** (§4.4).
Реализация — **MinIO** (для self-host/on-prem-опции) или **локальный S3** провайдера страны
(ADR-3). Доступ — только через `storage-gateway`; никаких внешних бакетов/CDN.

### 7.3. Redis — кэш, presence, pub/sub
- **Кэш** горячих метаданных (права, сессии), rate-limiting.
- **Presence** — эфемерные курсоры/выделения/viewport с TTL.
- **Pub/sub** — шина между нодами `multiplayer` (рассылка op/presence, когда редакторы файла
  попали на разные ноды) и доставка событий в `comments`.

### 7.4. Раскладка хранилищ по нагрузке (для сайзинга)
- PostgreSQL — рост с числом файлов/операций; драйвер — частота правок (лог) и число объектов.
- Redis — рост с числом одновременных presence-сессий и числом нод multiplayer.
- Объектное хранилище — рост с объёмом ассетов, частотой снапшотов и экспортов.

## 8. Деплой и эксплуатация

### 8.1. Старт — моно-сервер (ADR-4)
Всё в **одном `docker-compose` на одном VM**: nginx/traefik, auth, files, multiplayer, comments,
export-воркер, storage-gateway, postgres, redis, minio. Раздача **статики и WASM/JS-бандла —
локально с этого же сервера через nginx** (никакого внешнего CDN — ADR-3). TLS-сертификат —
локального УЦ/Let's-Encrypt-аналога, доступного в стране.

```
VM (T0):
  nginx ──┬── /          → статика (SPA, WebGL-движок, шрифты)
          ├── /api/*      → auth, files/projects/teams, comments
          ├── /ws/*       → multiplayer (WebSocket, sticky по умолчанию — 1 нода)
          └── /assets/*   → storage-gateway (presigned → minio)
  docker-compose: [postgres] [redis] [minio] [auth] [files] [multiplayer]
                  [comments] [export-worker] [storage-gateway]
```

### 8.2. Задел на горизонтальное масштабирование
Архитектура уже разрезана по сервисам; масштабирование вводится по тирам:
- **T1:** вынести БД и объектное хранилище на отдельные узлы; добавить **2-й+ узел multiplayer**
  за балансировщиком со sticky-сессиями и Redis pub/sub между ними; пул **export-воркеров**;
  реплики stateless-сервисов (auth, files).
- **T2:** **Kubernetes** — пул нод multiplayer с шардированием файлов по нодам (consistent
  hashing по `fileId`), HPA по CPU/соединениям для stateless-сервисов и воркеров,
  managed/кластерный PostgreSQL (реплики чтения), кластер Redis, распределённый MinIO/локальный
  S3.

### 8.3. Топология и драйверы нагрузки — передача в `docs/06` (infra-cost-estimator)
**Что масштабировать и чем оно драйвится** (для сайзинга по тирам T0/T1/T2):

| Компонент | Тип | Драйвер нагрузки | Стратегия масштабирования |
|---|---|---|---|
| **multiplayer (sync-узел)** | Stateful | **CPU при активных правках**; число одновременных активных редакторов на файл; число горячих файлов в памяти (RAM); число WS-соединений | Пул нод за балансировщиком, sticky-сессии, шардинг файлов по `fileId`; **главное узкое место (ADR-6)** |
| **export / render-воркеры** | Stateless (очередь) | Число и сложность задач рендера/экспорта (превью, тумбнейлы, ассеты); пиковая нагрузка при импорте/публикации | Горизонтальный пул воркеров по длине очереди |
| **PostgreSQL** | Stateful | Частота записи лога операций; число файлов/комментариев; запросы метаданных/прав | Вертикально → реплики чтения → партиционирование/кластер |
| **Redis** | Stateful | Число presence-сессий; объём pub/sub-трафика между нодами; кэш-трафик | Вертикально → кластер; отдельные инстансы под presence/pub/sub при росте |
| **Объектное хранилище (MinIO/S3)** | Stateful | Объём ассетов; частота снапшотов; объём/частота экспортов и раздачи | Вертикально → распределённый режим |
| **storage-gateway** | Stateless | Трафик загрузки/выдачи ассетов; число presigned-запросов | Реплики за балансировщиком |
| **auth, files/projects/teams, comments** | Stateless | RPS API; число активных сессий; проверки RBAC | Реплики + HPA |
| **nginx/балансировщик + раздача статики/WASM** | Stateless | Трафик статики/WASM (без CDN — всё локально); число WS-апгрейдов | Несколько инстансов; локальный кэш статики |

**Ключевой вывод для сайзинга:** на горячем пути критичны **multiplayer-ноды (CPU/RAM)** и
**PostgreSQL (запись лога)**; раздача статики/WASM **без CDN** добавляет нагрузку на исходящий
трафик балансировщика — это надо учесть в стоимости трафика локального провайдера.

## 9. Безопасность и резидентность

1. **Изоляция арендаторов (tenant isolation).** Все данные несут `team_id` по цепочке;
   каждый запрос проходит RBAC-проверку (auth) и фильтрацию по тенанту. На T0 — логическая
   изоляция (row-level) в общей БД; для Org/Enterprise — опция выделенной БД/схемы или отдельного
   инстанса (резидентность под клиента, см. `docs/01` §6).
2. **Шифрование.** TLS на всех внешних соединениях; шифрование данных at-rest на дисках БД и
   объектного хранилища; секреты — в защищённом vault, не в образах.
3. **RBAC.** Роли owner/admin/editor/viewer на уровнях team/project/file; шаринг по ссылке с
   ограничением прав; проверки централизованы в auth + files.
4. **Аудит (audit log).** Лог значимых действий (доступ, шаринг, экспорт, изменение прав) в
   PostgreSQL — для регулируемых отраслей и расследований (опирается на лог операций §5.5).
5. **Локальная юрисдикция / резидентность.** Вся инфраструктура и все данные — внутри страны
   (ADR-3). Нет внешней телеметрии, шрифтовых/аналитических CDN, внешних бакетов. Платежи — через
   локальных провайдеров (вне этого документа).
6. **Защита от злоупотреблений.** Rate-limiting (Redis) на auth и WS; валидация размеров
   загрузок; presigned-URL с TTL для ассетов.

## 10. Импорт `.fig` (ADR-7) — отдельный трек

См. `src/07-анализ-конкурентов.md` (Pixso/MasterGo с импортом `.fig`).

### 10.1. Контекст и риск
`.fig` — **проприетарный бинарный формат** Figma; официальной спецификации нет. Импорт — сильный
фактор миграции (как у Pixso/MasterGo), но технически рискованный и хрупкий: формат может
меняться, полное соответствие недостижимо. По ADR-7 — **не блокирует MVP**, идёт отдельным
треком фазы роста.

### 10.2. Архитектурный подход
- **Изолированный сервис-импортёр (importer)** вне горячего пути: принимает `.fig`, парсит во
  **внутреннюю модель документа** (§4), пишет результат как новый файл (снапшот). Запускается как
  фоновая задача (как export-воркеры), масштабируется числом воркеров.
- **Два возможных пути парсинга** (оценить на спайке):
  1. **Через Figma REST API** — если у пользователя есть доступ к Figma: тянуть документ как
     структурированный JSON и маппить в нашу модель (надёжнее, но требует доступа к Figma у
     пользователя — что на целевых рынках как раз проблематично).
  2. **Прямой разбор `.fig`** — реверс публично описанной структуры (kiwi-схема Figma, ZIP/бинарь),
     маппинг узлов/свойств в нашу модель. Рискованно, но не зависит от доступа к Figma.
- **Маппинг с деградацией:** неподдерживаемые фичи (сложные эффекты, плагин-данные) импортируем
  «как можно ближе» с отчётом о потерях, а не падаем.
- **Без проприетарного кода** — только публичные источники (CLAUDE.md §9): анализ формата
  ведётся по открыто описанным схемам, чужой код не воспроизводится.

### 10.3. Риски
Хрупкость к сменам формата; неполное соответствие визуала; юридическая аккуратность
(реверс-инжиниринг). Поэтому — отдельный трек с собственным спайком и критериями приёмки, не на
критическом пути MVP.

## Приложение A. Сводка хэндоффов

**(а) Предложенный финал ADR-5** — см. §3.4 (рендерер MVP = TS+WebGL за абстракцией `Renderer`;
WASM — фаза масштабирования).

**(б) Сервисы и драйверы нагрузки для infra-cost-estimator** — таблица §8.3. Главные драйверы:
multiplayer-ноды (CPU/RAM, активные редакторы), PostgreSQL (запись лога операций), исходящий
трафик статики/WASM без CDN.

**(в) Решения и термины, внесённые в `docs/00`** (статус — выполнено):
- **ADR-5 → «Принято»** с формулировкой §3.4 (рендерер TS+WebGL).
- **ADR-12 — Открытый формат файла:** документ сериализуется в открытый ZIP
  (`document.json` + ассеты SVG/PNG) для экспорта/архива; внутреннее runtime — компактное
  (плоская карта + лог + бинарные снапшоты). Урок Penpot против бинаря Figma.
- **Термины (внесены в глоссарий):** Снапшот (Snapshot), Лог операций (Operation log),
  Sticky-сессия (Sticky session), Изоляция арендаторов (Tenant isolation), Реparenting
  (Reparenting), Джиттер (Jitter — случайная составляющая дробного индекса против коллизий).
