# 03. Техническая архитектура Figma

> Источники — в [`06-источники.md`](./06-источники.md). Анализ по публичным инженерным
> публикациям Figma и экспертным разборам. Проприетарный код не воспроизводится.

## 3.1. Рендеринг

### C++ → WebAssembly
Ядро рендерера Figma написано на **C++** и компилируется в **WebAssembly (WASM)** с помощью
**Emscripten** для исполнения в браузере. Тот же C++-код собирается и в нативное приложение
(x64/arm64) для серверного рендеринга, тестирования и отладки
([Figma: powered by WebAssembly](https://www.figma.com/blog/webassembly-cut-figmas-load-time-by-3x/)).
Переход на WASM ускорил загрузку примерно **в 3 раза** по сравнению с предыдущим
asm.js-подходом (см. там же).

### Кастомный tile-based GPU-рендерер
Figma не использует DOM/SVG для отрисовки контента холста — это слишком медленно для тысяч
узлов. Вместо этого реализован **собственный высокооптимизированный тайловый (tile-based)
рендерер**, целиком работающий на GPU, с поддержкой масок, блюра, дизеринг-градиентов, режимов
наложения (blend modes), вложенной прозрачности слоёв и полного сглаживания (anti-aliasing)
([Building a professional design tool on the web](https://www.figma.com/blog/building-a-professional-design-tool-on-the-web/)).

### Кривые по алгоритму Loop–Blinn
Векторные кривые (заливки, обводки) отрисовываются на GPU; для этого применяется техника
рендеринга кривых типа **Loop–Blinn** (вычисление принадлежности пикселя кривой в шейдере), что
позволяет избежать дорогой триангуляции и держать всё на GPU
([Made by Evan: Figma](https://madebyevan.com/figma/)).

### Обход DOM/SVG ради производительности
Сознательный отказ от браузерного дерева отрисовки в пользу единого WebGL/WebGPU-полотна —
ключевое архитектурное решение, дающее предсказуемую производительность на больших документах.

### Миграция WebGL → WebGPU (с 2023)
В 2023 году с появлением **WebGPU** в Chromium Figma начала миграцию с WebGL. WebGPU открывает
оптимизации, недоступные в WebGL: **compute-шейдеры** (вынос работы с CPU на GPU, например
рендеринг блюра), **WGSL** (язык шейдеров), **MSAA** (мультисэмпловое сглаживание). Это заняло
около года работы
([Figma Rendering: Powered by WebGPU](https://www.figma.com/blog/figma-rendering-powered-by-webgpu/)).

### Слой связывания (bindings) C++ ↔ UI
UI-оболочка (панели, меню, инспектор) написана на **TypeScript/React**, а холст — на C++/WASM.
Между ними есть **слой биндингов (bindings)**, через который React-UI читает/меняет состояние
сцены в WASM-памяти ([Medium: Figma is a Game Engine](https://medium.com/@nike_thana/figma-is-a-game-engine-not-a-web-app-how-c-and-wasm-broke-the-react-ceiling-8ed991bea48f)).

> **Связь с ADR-5 (принято).** Figma-путь (C++/WASM + кастомный GPU-рендерер) даёт лучшую
> производительность, но дорог в разработке. Для нашего MVP выбран более лёгкий рендерер —
> **TypeScript + WebGL** за абстракцией `Renderer` (Canvas2D отвергнут как CPU-bound), с
> нативным Rust/WASM-движком как целью фазы масштабирования. Детали — в `docs/04`.

## 3.2. Мультиплеер (Multiplayer)

### Server-authoritative модель (не чистый CRDT и не OT)
Совместное редактирование у Figma — **серверно-авторитетное (server-authoritative)**: при
открытии файла клиент устанавливает **WebSocket**-соединение с sync-сервисом, который
принимает и рассылает изменения, выполняя валидацию, упорядочивание и разрешение конфликтов
([How Figma's multiplayer technology works](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)).
Это **не** чистый CRDT и **не** OT: поскольку сервер централизован и является арбитром, он
определяет порядок операций без векторных часов и сборки «надгробий» (tombstones), что
упрощает и ускоряет систему.

### Property-level Last-Writer-Wins по логическим часам
Конфликт возникает, когда два клиента меняют **одно и то же свойство одного узла** — побеждает
последнее по серверному порядку значение (**property-level Last-Writer-Wins, LWW**). Это похоже
на LWW-register из CRDT-литературы, но серверу не нужна метка времени, так как он сам задаёт
порядок событий (там же). Упорядочивание операций опирается на **логические часы (logical
clock)**.

### In-memory состояние, до ~200 редакторов на документ
Sync-сервер держит **состояние документа в памяти (in-memory)** для быстрой обработки, а
долговременное хранение (персистентность) — отдельно. По публичным разборам, один документ
поддерживает порядка **до ~200 одновременных редакторов**
([Making multiplayer more reliable](https://www.figma.com/blog/making-multiplayer-more-reliable/),
[sujeet.pro: Figma multiplayer](https://sujeet.pro/articles/figma-multiplayer-infrastructure)).

> **Связь с ADR-6 (принято).** Наш протокол синхронизации воспроизводит именно эту модель:
> server-authoritative property-level LWW по логическим часам поверх WebSocket, fractional
> indexing для порядка/реparentinга, in-memory состояние на sync-узле и отдельная
> персистентность. Узкое место — CPU sync-узла при активных правках (см. сайзинг `docs/06`).

## 3.3. LiveGraph — real-time read-path

**LiveGraph** — отдельная подсистема **чтения** real-time данных (не путать с write-path
мультиплеера). Это слой поверх **Postgres**, позволяющий фронтенду подписываться на данные
через **GraphQL-подписки** и получать живые обновления за миллисекунды
([LiveGraph: real-time data fetching at Figma](https://www.figma.com/blog/livegraph-real-time-data-fetching-at-figma/)).

Ключевая идея — **тейлинг лога репликации Postgres**: все мутации строк попадают в
**write-ahead log (WAL)**; LiveGraph переиспользует этот поток, доставляя **инкрементальные
апдейты** подписчикам, вместо нагружающего БД поллинга. Source of truth остаётся в БД; read-path
не обязан знать о записях клиентов. Инициатива **«LiveGraph 100x»** масштабирует эту систему по
нагрузке чтения/обновлений
([Keeping It 100(x)](https://www.figma.com/blog/livegraph-real-time-data-at-scale/)).

> **Важно для нас.** LiveGraph отвечает за «живые» метаданные (комментарии, присутствие на
> уровне файлов, списки проектов/файлов, статусы), а не за содержимое холста. Разделение
> read-path (LiveGraph) и write-path (мультиплеер) — полезный архитектурный паттерн.

## 3.4. Undo / Redo

Undo/redo в совместной среде нетривиальны, потому что между отменой и повтором другой
пользователь мог изменить документ. Описанные публично инварианты:
- **undo меняет историю redo, а redo меняет историю undo** (они взаимно влияют);
- ключевой инвариант: **undo → copy → redo** должен оставлять документ в согласованном виде
  (отмена с последующим повтором не теряет/не дублирует изменения)
  ([Figma multiplayer blog](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)).

Undo локален для пользователя (отменяются собственные действия), но согласуется с серверным
порядком операций.

## 3.5. Offline (ограниченный)

Полноценной офлайн-работы у Figma нет: **офлайн ограничен уже открытыми файлами** — можно
продолжать редактировать загруженный документ, изменения синхронизируются при восстановлении
связи. Открыть произвольный файл без сети нельзя.

> **Контекст ADR-3.** Для рынков с ограниченным доступом ценность офлайна/локального
> развёртывания выше, чем у Figma. Это конкурентное преимущество (ср. Sketch/Lunacy offline,
> Penpot self-host в `07`).

## 3.6. Масштабирование

- **Рендеринг** масштабируется на клиенте (GPU) + WASM; серверный рендер для превью/экспорта.
- **Мультиплеер** — горизонтально по документам (шардирование по файлам; один файл —
  ограниченное число редакторов и in-memory узел).
- **Read-path (LiveGraph)** — масштабируется отдельно («100x»), тейлингом WAL и репликами.
- **Хранение** — Postgres + объектное хранилище для бинарных ассетов/версий.

> **Связь с ADR-4.** Мы стартуем с моно-сервера (docker-compose на одной VM) и масштабируемся
> по тирам T0→T1→T2; архитектура сервисов модульная (рендер/sync/read-path/хранение
> разделимы), но на старте упакована вместе.
